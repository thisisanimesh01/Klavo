# Credential Rotation, Secret Remediation & Invalidation Runbook (SEC-09)

This document establishes the official operational standard, remediation procedures, threat assessment, session invalidation protocols, and automated regression guards for secret and credential lifecycle management across the Klavo platform.

---

## 1. Executive Summary & Zero-Trust Posture

During early prototype development in November 2025 (`0a59b32` and `afa8390`), temporary configuration files were committed to Git history before comprehensive `.gitignore` rules were established in Milestone SEC-02 (`8a5deb3`).

Under modern Zero-Trust and DevSecOps principles:
> [!IMPORTANT]
> **Git history scrubbing does NOT remediate compromised credentials.**
> Once a secret, password, or key is pushed to a remote repository or fork, it must be considered **permanently compromised** and revoked at the source authority (MongoDB Atlas, Cloud Identity Provider, OAuth Authorization Server).
>
> In accordance with safety invariants, **no Git history was rewritten and no external provider accounts were modified without explicit authorization**. This runbook specifies the precise, step-by-step procedures the system owner/maintainer must execute to achieve complete remediation.

## 3. Step-by-Step Credential Rotation Runbooks

### 3.1 MongoDB Atlas Credential Rotation & Network Hardening

Execute the following in the **MongoDB Atlas Web Console**:

1. **Step 1: Network Access Verification**:
   - Navigate to **Security > Network Access**.
   - Verify that IP allowlists restrict connections strictly to:
     - Application hosting servers / container clusters (e.g. AWS Elastic IP, Render outbound CIDR).
     - Remove `0.0.0.0/0` (allow access from anywhere) if currently active.
2. **Step 2: Create New Database User**:
   - Navigate to **Security > Database Access > Add New Database User**.
   - Authentication Method: **Password**.
   - Username: `klavo_prod_v2` (or environment-specific identifier).
   - Password: Click **Autogenerate Secure Password** (minimum 32 characters).
   - Database User Privileges: Assign **Read and write to any database** or restrict strictly to database `klavo` (`readWrite@klavo`).
3. **Step 3: Update Application Environment**:
   - Update `MONGO_URI` in your production secret manager (AWS Secrets Manager, GCP Secret Manager, or environment configuration) with the new credentials:
     ```
     mongodb+srv://klavo_prod_v2:<NEW_AUTOGENERATED_PASSWORD>@<cluster>.mongodb.net/klavo?retryWrites=true&w=majority
     ```
4. **Step 4: Zero-Downtime Rolling Deployment**:
   - Trigger a rolling restart or deployment of the Klavo backend service.
   - Verify successful connection in application logs:
     ```json
     {"severity":"INFO","message":"MongoDB connected successfully"}
     ```
   - Verify health check: `curl -f https://app.yourdomain.com/api/health/ready` returns `200 OK`.
5. **Step 5: Revoke Legacy Database User**:
   - Return to **Security > Database Access**.
   - Delete the old database user that existed in historical commits.
   - Any historical connection strings will immediately fail to authenticate.

### 3.2 JWT Signing Key Rotation & Session Invalidation Protocol

Rotating `JWT_SECRET` cryptographically invalidates all outstanding client tokens issued under the old key, terminating stale sessions across all devices.

1. **Step 1: Cryptographic Key Generation**:
   - Generate a cryptographically secure 256-bit (64-character hex) secret:
     ```bash
     node -e "console.log(crypto.randomBytes(32).toString('hex'))"
     ```
2. **Step 2: Update Server Configuration**:
   - Set `JWT_SECRET=<GENERATED_64_CHAR_HEX>` in the backend production environment.
3. **Step 3: Deploy Backend Instances**:
   - Restart the backend Node.js instances.
4. **Step 4: Client Session Invalidation Behavior**:
   - When users make subsequent requests, the backend JWT verification in `authMiddleware.js` and `io.use()` fails with `JsonWebTokenError: invalid signature`.
   - The backend responds with `401 Unauthorized`.
   - Frontend Axios response interceptors (`frontend/src/api/apiClient.js`) automatically intercept the `401`, clear `localStorage` credentials, purge Redux store auth state, and cleanly redirect users to `/login`.
   - Users simply log in again with their email/password or Google OAuth, receiving fresh tokens signed with the new secret.

### 3.3 Google OAuth 2.0 Client Secret Rotation

Execute the following in the **Google Cloud Console**:

1. **Step 1: Navigate to API Credentials**:
   - Go to **Google Cloud Console > APIs & Services > Credentials**.
2. **Step 2: Inspect OAuth 2.0 Client ID**:
   - Select the Web Application Client ID used for Klavo.
   - Verify authorized JavaScript origins (`https://app.yourdomain.com`) and redirect URIs match your production domain.
3. **Step 3: Rotate Client Secret**:
   - Click **Reset Secret** to generate a replacement client secret.
   - Download or copy the new client secret into your production secrets manager.
4. **Step 4: Update Backend Configuration**:
   - If server-side Google token verification or code exchange is configured, update the backend environment with the new client secret.
5. **Step 5: Delete Old Secret**:
   - In Google Cloud Console, delete the previously compromised secret key so it can no longer be used.

## 4. Automated Secret-Leak Regression Guards

To prevent accidental commits of secrets going forward, Klavo integrates automated static secret scanning into the core toolchain and continuous integration pipeline:

### 4.1 CLI Scanner (`scripts/scan_secrets.js`)
Developers and CI can scan all Git-tracked files at any time:
```bash
npm run scan:secrets
# or node scripts/scan_secrets.js
```
The scanner checks:
- Private key headers (`-----BEGIN ... PRIVATE KEY-----`)
- Live AWS access keys (`AKIA[0-9A-Z]{16}`)
- MongoDB URIs with embedded passwords (`mongodb://user:pass@host`)
- Live Bearer JWT tokens (`Bearer eyJ...`) outside of authorized test mocks
- Any tracked `.env` file (strictly enforcing that only `.env.example` templates may be tracked)

### 4.2 GitHub Actions CI Enforcement (`.github/workflows/ci.yml`)
The CI workflow automatically executes `node scripts/scan_secrets.js` on every pull request and push to `main`. If any tracked file contains an exposed secret pattern, the build immediately fails with a non-zero exit code.

### 4.3 Environment Startup Invariant Checks (`backend/src/config/env.js`)
At boot time in production (`NODE_ENV=production`), Klavo validates:
- `JWT_SECRET` is at least 32 characters long.
- `JWT_SECRET` does not contain insecure default placeholders (e.g. `change_me`, `replace_with`, `test_jwt_secret`).
- `MONGO_URI` does not contain template placeholders (e.g. `<db_password>`, `<db_user>`).
- If invalid, the process exits cleanly **without logging the secret value**.

## 5. Pre-Commit Best Practices for Developers

1. Never remove `.env` from `.gitignore`.
2. Always inspect `git diff --staged` before committing.
3. Use environment variable placeholders (`<db_user>`, `<db_password>`) in documentation and example files.
4. Store shared team development secrets in an encrypted password manager (1Password, Bitwarden, AWS Secrets Manager) rather than Slack, email, or repository issues.
